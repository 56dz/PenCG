## 0. 一句话

bug1 的停推判据不是「起播后固定 4m18s」，而是 **每一个 WebSocket 会话都只有约 250 秒寿命**（每次 `wsOpen` 重新计时）。历史那个「4m18s」看着像定值，是**起播冷启动 40~60s** 与 **会话 250s** 两个量级叠加后抖动被掩盖的错觉。

既然寿命是可预测的，就**曾**尝试不等它停了再救：在 230s 主动换一个新会话。**这条路已被真机否掉** —— 换会话必然换机位、必然重拉对局容器，玩家看到的是游戏从头开始（§9）。

因此本文档分两部分读：

- **§1–§2 仍然有效**，是「每 WS 会话约 250s」这个判据的推导与实测，与方案开关无关；
- **§3–§7 是已关闭方案的存档**，讲当时怎么算阈值、怎么实现、怎么验证。读它们请记住结论是「不启用」。

## 1. 怎么从「每日志」推出 250s

原来那句「4m19 / 4m18 / 4m18，精度 ±1s，像服务端定时器」，测量的是**从起播到停推**的总时长，其中混着两段性质完全不同的时间：

```
起播 → wsOpen          ：容器冷启动 + 鉴权 + 首帧，40~60s 量级，抖动很大
wsOpen → 网关停推      ：这才是服务端计时器管辖的那一段
```

只有把「停推时刻」减去「`wsOpen` 时刻」，拿到的才是真正被计时的那个量。判据也很直接：

- **停推时刻 = `[play] stall detected` 行的时刻 − 该轮的 `STALL_RX_MS`**（当时是 20000ms；2026-11-14 02:19 起已收紧为 8000ms，见 `docs/BUGFIX-bug1-stallguard.md`）。
- **wsOpen 时刻**：2026-11-14 起 probe 行带 `sess=`（见 §4.2），可直接读；早期日志靠 `[play] probe` 里第一次出现 `ws=open` 的时间点。

`BUG1-KEEPALIVE-PROTOCOL.md` 当初为什么没能定案，正是因为它只在「ticket 时刻 / WS 建立 / 最后一次操作」三个起点之间做算术，而**没有把每一次 `wsOpen` 单独当作一局的起点**——L2 重连、手动重连都会产生新的 `wsOpen`，那些会话的寿命从来没人单独量过。

## 2. 三局实测（2026-11-14 01:12–01:30）

设备 `9D91500007505171`，X6 Pro，原神 `yssy`，同一次测试连续三局，每一局都是不同的会话起点：

| 会话 | `wsOpen` 时刻 | 停推时刻 | 本次会话寿命 | 起点说明 |
|---|---|---|---|---|
| A | 01:12:52 | 01:16:59 | **247s** | 首次起播 |
| B | 01:17:24 | 01:21:37 | **253s** | `[play] stall` L2 重连后的新会话 |
| D | 01:25:09 | 01:29:17 | **248s** | 手动「重新申请机位」后的新会话 |

**均值 249.3s，离散 ±3s。**

这个离散度是关键：如果真是「ticket + 300s」那种绝对定时器，三局的差值应该稳定在 1 秒级（历史那三次 4m19/4m18/4m18 就是这个样子）。而**从 `wsOpen` 起算的三局是 247/253/248**，±3s 的抖动更像「服务端从会话建立开始数的计时器 + 少量调度误差」。

> 会话 C 缺失（编号跳过）是因为那一次重连失败、没有产生有效会话，不是漏记。

**另一条独立证据**：`BUGFIX-bug1-stallguard.md` §6.4 早就写过「L2 之后是否重新计时未知」。这三局直接回答了它 —— **会重新计时**，而且新会话同样只有约 250s。这也是为什么 STALLGUARD 的第 2 级（L2 重连）能救回画面：它本质上就是换了个新会话。

### 2.1 与 2026-11-13「没有复现」的冲突（未解，必须记下来）

`BUG1-KEEPALIVE-PROTOCOL.md` §1.1 记了一件与「每会话 250s」直接冲突的事：

- 2026-11-13 17:58:04 起播 → 18:25:15 仍在出帧，`rx` 从 250 单调涨到 131099、`fps=29`，**跨越 4m18s / 8m / 16m 三个窗口都没有冻结**；
- 18:47:20 起播 → 18:50:43 `rx=20359 fps=19`，也没有冻结。

按「每会话 ≈250s」的模型，一局连续跑 27 分钟**必然经历过若干次会话重建**，而 `rx` 却在同一份日志里从 250 单调涨到 131099 —— 这说明那 27 分钟里**很可能一直没有重建过会话**，与「每会话 250s」矛盾。

目前能想到的三种解释，**都没有证据**：

| 解释 | 需要什么证据才能坐实 |
|---|---|
| ① 那次 RTCP RR 合入确实改变了服务端行为（服务端把「收到 RTCP RR」当成活跃信号） | 需要 `rrSent` 与停推时刻的对照样本（那两局 RR 已生效） |
| ② 那两局可能是另一种播放路径 —— 画质档位 / 机位类型不同，服务端计时策略不同 | 需要对比 `[play] boot q=` 与机位字段 |
| ③ 250s 不是绝对上限，而是「无操作」条件下的上限 | 需要做「有操作 vs 无操作」的对照组 |

**这条冲突不影响 230s 主动续命的安全性**（提前换会话最坏也只是多换一次），但它意味着**「每会话 250s」这个判据还不完整**。做长跑验证时请专门记录两件事：`renew=` 是否真的每 ~230s 递增；以及有没有哪一局越过 250s 还没停 —— 后者正是这条冲突的直接证据。

## 3. 230s 阈值与 60s 冷却的推导

> ⚠️ **本节推导的是「如果要做主动续命，阈值该取多少」，不是「该不该做」。**
> 「该不该做」已在 2026-11-14 02:09 被真机否掉（见 §9）。阈值推导本身没有错，错的是当时对「换会话的代价」估计严重不足 —— 以为代价是 2~4 秒，实际是**游戏重开、进度清零**。

### 3.1 为什么是 230s

三个约束同时成立才定下这个数：

| 约束 | 数值 | 说明 |
|---|---|---|
| 必须早于最短观测寿命 | 最短 247s | 230s 比它早 17s |
| 必须包容观测抖动 | ±3s | 230s 留的余量（17s）是抖动的 5 倍以上 |
| 必须与 STALLGUARD 判据不重叠 | `STALL_RX_MS`（当时 20s，现 8s） | 若续命设在 245s，一旦某局真在 240s 停推，用户仍要先看满一个 STALLGUARD 检测窗口才等到自愈 |

所以取 **230s**：比 247s 早 17s（安全），又比「245s 会踩到 STALLGUARD 的检测窗口」更早（两条防线不重叠）。

> **2026-11-14 02:09 真机更正：上面这句「主动续命的代价是 2~4 秒」是错的。**
> 当时以为「换会话」只是「重连 + 等新 IDR 出画」。实测发现：换会话必然换机位，**必然重新拉起一个对局容器 = 游戏从头开始**，玩家看到的是回到启动画面、进度清零（三次实测黑屏 9/8/7s、音频恢复 11/19/18s，见 §9）。
>
> 所以真实取舍不是「2~4 秒 vs 20 秒」，而是「**游戏重开** vs 十几秒静止画面」。后者显然更可接受 —— 这就是本方案默认关闭的原因。

### 3.2 为什么是 60s 冷却

`ACTIVE_RENEW_GUARD_MS = 60000` 是**两次主动续命之间的最小间隔**，防的是「换完会话立刻又到期」造成的连环重连：

- 正常情况换会话 2~4 秒就出画了，60s 足够；
- 若 60s 还没恢复，说明网关侧有真问题，**再换一次只会白烧机位**，此时应该交给 STALLGUARD 走完它的三级流程。

### 3.3 常量与位置

| 常量 | 值 | 位置 | 说明 |
|---|---|---|---|
| `ACTIVE_RENEW_MS` | **`0`（默认关闭）**；曾为 `230000` | `PenCG/src/pages/play/play.vue:265` | 0 = 关闭（当前值）；改回 `230000` 即重新启用（见 §9） |
| `ACTIVE_RENEW_GUARD_MS` | `60000` | `PenCG/src/pages/play/play.vue:269` | 两次主动续命的最小间隔 |

两个常量紧跟在 `var STALL_MAX_TRIES = 3;`（`:223`）之后，上面有约 38 行注释记录了 250s 判据、`onReapply` 被踢的实测、以及「默认关闭」的三次实测结论（`:227-264`），改之前请先读。

## 4. 实现

### 4.1 状态与刷新点

| 项 | 位置 | 说明 |
|---|---|---|
| `wsOpenAt: 0` | `play.vue:383` | 本次 WS 会话建立时刻（`Date.now()`）。0 = 还没连上 |
| `renewAt: 0` | `play.vue:384` | 上一次主动续命的时刻。0 = 本局还没主动续命过 |
| `renewCount: 0` | `play.vue:385` | 本局主动续命次数（只用于日志与探针） |
| 每次 `wsOpen` 刷新基准 | `play.vue:962`（`onMedia` 的 `t==='ws'` / `ev.state === 'open'` 分支） | **必须是每一次 open**：L2 自愈、主动续命、用户点重连都会产生新会话，每个新会话都只有约 250s |
| 进新一局清零 | `play.vue:753-755` | `boot()` 里 `wsOpenAt / renewAt / renewCount` 全部归零 |
| `tick()` 里调用 | `play.vue:1434` | 紧跟在 `this.checkStall(now, s)`（`:1426`）之后 |

### 4.2 probe 行新增两个字段

`play.vue:1465-1466`：

```
[play] probe stage=live ... tries=0 sess=187s renew=0 keep=on
```

- `sess=Ns`：本次会话已存活秒数（`wsOpenAt` 为 0 时打 `-`）
- `renew=N`：本局主动续命次数

这两个字段是**验证主动续命是否work的唯一入口**，详见 §5。

### 4.3 `checkRenew(now, s)`（`play.vue:1521`）的门

按执行顺序，遇到第一个成立的就 `return`：

| 门 | 条件 | 为什么 |
|---|---|---|
| 1 | `this.dead` | 页面已销毁 |
| 2 | `!ACTIVE_RENEW_MS` | 开关关闭 —— **当前默认值就是 0，所以走到这一行必定 `return`** |
| 3 | `!this.wsOpenAt` | 还没连上过网关 |
| 4 | `this.hiddenSince` | 退后台不续命（与 `checkStall` 同理由：此时网络可能被系统挂起，重连白烧机位） |
| 5 | `this.busy` | 重连/申请/退出正在进行 |
| 6 | `this.stallTries > 0` | **STALLGUARD 正在自愈，让它走完** |
| 7 | `this.stallL1Timer` | L1 已发补帧、正在等复查（`STALL_L1_WAIT_MS`，现 3s） |
| 8 | `!this.vizOn` | 画面本来就没出来（还在等首帧），换会话毫无意义 |
| 9 | `s !== 'live'` | 只在真正出画的稳定态续命 |
| 10 | `this.wsState !== 'open'` | WS 没连着 |
| 11 | `this.renewAt && now - this.renewAt < ACTIVE_RENEW_GUARD_MS` | 冷却期（§3.2） |
| 12 | `age < ACTIVE_RENEW_MS` | 还没到寿命阈值 |

门 4~7 与 `checkStall` 顶部的门**刻意保持一致**——两条防线不许同时动作，否则会互相把对方刚设的 `stallTries` / 计时基准改掉（本项目已经踩过这个坑）。

### 4.4 `renewNow(now, age)`（`play.vue:1538`）做的事

```
renewAt = now
renewCount++
wsOpenAt = now          ← 立刻重置基准：若重连失败，下一轮 230s 后才会再试
stallWindowReset(now)   ← 换机位要 5~10s，期间 checkStall 的计时会一直走，必须重开窗口
logWarn('[play] renew: 会话已存活 Ns（阈值 Ns）→ 主动换会话（第 N 次），避免网关停推')
vizOn = false
stage = 'waiting'
tip = '正在切换画面通道…'
onReapply()             ← 重新申请机位，不是 onReconnect（复用网关会被踢，见 §9.3）
```

> **2026-11-14 更正**：原稿这里写的是 `onReconnect()`。实现在 01:51 真机被踢之后已改成 `onReapply()`；而 `onReapply()` 换机位正是「游戏重开」的根源（§9.2）。

**刻意不写 `stallTries`**：主动续命是计划内行为，不该占用 STALLGUARD 的自愈额度（3 次），否则真正遇到弱网停推时用户只剩 2 次机会。这是本文档与 `stallHealL2` 唯一的语义差别。

## 5. 与 STALLGUARD 的分工

| | 触发条件 | 谁先发生 | 用户可见代价 | 计不占自愈额度 |
|---|---|---|---|---|
| **主动续命**（本文档，**已默认关闭**） | `sess >= 230s` | 只要启用就永远先发生 | **游戏重开、进度清零**（换机位 = 重拉对局容器） | 不占（不写 `stallTries`） |
| **STALLGUARD**（`BUGFIX-bug1-stallguard.md`，**现行唯一路径**） | `rx` 冻结 8s | 停推后必然走到 | 8s 静止 + L2 黑屏（实测停推→恢复 ≈ 11s），进度不丢 | 占（最多 3 次） |

**降级关系（原设计）**：主动续命是「计划内维护」，STALLGUARD 降级为「兜底抢修」。

> **2026-11-14 现状**：主动续命已默认关闭，**STALLGUARD 是唯一路径**，不再是兜底。下面这段「什么情况下被门拦住」只在重新启用后才有意义，保留作存档：

- 用户退后台了（门 4）—— 但那时用户也看不见，无所谓；
- 画面还没出来（门 8）—— 首帧都没到，换会话无意义；
- 刚换过会话还在冷却（门 11）—— 60s 内不再折腾；
- `stage !== 'live'`（门 9）—— 此时 `checkStall` 也不动作，两边都不抢。

反过来，STALLGUARD 已经把 `stallTries` 抬起来之后（门 6），主动续命**不会插手**，避免把 STALLGUARD 刚设的计时基准改掉。

## 6. 怎么验证 / 怎么关闭

### 6.1 验证（唯一入口是 probe 行的 `sess=` 与 `renew=`）

> 下面这套判据**只在 `ACTIVE_RENEW_MS` 被改成非 0 之后才适用**。当前默认关闭，`renew:` 行永远不会出现 —— 这不代表故障。

```bash
# 变量先备好（路径不能写死，见 docs/VERIFY-playbook.md §0.2）
ADB="./env/adb/adb.exe -s 9D91500007505171"
P=$($ADB shell 'pidof miniapp' | tr -d '\r')
L=$($ADB shell "readlink /proc/$P/fd/1" | tr -d '\r')
echo "LOG=$L"

# 1) 看会话寿命与续命次数（每 20s 一行）
$ADB shell "grep -a '\[play\] probe' \"$L\" | tail -40"

# 2) 看主动续命有没有真的发生
$ADB shell "grep -a '\[play\] renew:' \"$L\" | tail -10"
```

**健康态的判据**（三条同时成立）：

| # | 看到什么 | 说明 |
|---|---|---|
| 1 | 每 **~230s** 出现一条 `[play] renew: 会话已存活 23Ns（阈值 230s）→ 主动换会话（第 N 次），避免网关停推` | 主动续命按预期触发（**仅在重新启用后**） |
| 2 | 该行前后的 probe 里 `sess=` **短暂归零**（换会话后重新计时），`renew=` 递增 1 | 基准确实被重置了 |
| 3 | `rx` 短暂归零后**继续涨**、`fps` 恢复、**全程没有出现 `[play] stall detected`** | 停推被提前规避，STALLGUARD 没被惊动 —— **注意：这一条即使成立也不代表方案可用**，因为判据只看「画面回来了没有」，看不到「游戏进度没了」 |

**失败态**：

| 看到什么 | 结论 |
|---|---|
| `sess=` 一路涨过 260s、`renew=` 恒 0 | 先确认 `ACTIVE_RENEW_MS` 是不是 0（**当前默认就是 0，这是预期行为**）；若确实是 230000 却没触发，再看是否长期 `hiddenSince` / `!vizOn` / `stage!=='live'` 被门拦住 |
| `renew=` 涨了，但随后仍出现 `[play] stall detected` | 续命发生了但没救回来 → 走 STALLGUARD；若 `renew=` 短时间内连涨多次，说明冷却失效或网关拒连 |
| `renew=` 涨、`sess=` 却仍从旧值继续涨 | `wsOpenAt` 没在 `ev.state==='open'` 时刷新（`play.vue:934`）—— 这是最容易回归的写法错误 |
| 完全没有任何 `renew:` 行、但 `sess=` 正常涨 | 阈值未到就退出了，或 `ACTIVE_RENEW_MS` 被改成 0 |

### 6.2 开关（当前状态：**已关闭**）

`PenCG/src/pages/play/play.vue:265` 现在是：

```js
var ACTIVE_RENEW_MS = 0;   /* 0 = 关闭；改回 230000 即重新启用 */
```

- **保持关闭**（默认）：不用做任何事。`checkRenew()` 的门 2 会立刻 `return`，其余逻辑不动，STALLGUARD 与 `checkFreeze` 完全不受影响。
- **重新启用**：把 `0` 改成 `230000`，并先读 §9 —— 重新启用就意味着**每 230 秒游戏重开一次**。除非发现某个游戏/某类机位换会话不重开容器（完全未测），否则不建议。

关闭的完整理由见 §9，不要只按 §7 第 1 条（网关惩罚）来理解 —— 真正的否决理由不是「网关会不会惩罚」，而是「玩家会丢进度」。

## 7. 已知未验证项（诚实标注）

> 本节列的是**方案本身**的未知项。方案已默认关闭，所以这些项现在的价值是「万一将来重新启用，先补哪些功课」；其中第 7 条已经不再是未知项，而是被实测改掉的设计，保留原文位置并加更正。

1. **网关对「频繁重连」是否有惩罚 —— 完全未测。** 每 250 秒换一次会话，一小时就是 14 次；官方客户端会不会因此降画质、限流、或拒绝重连，我们没有数据。这是本方案最大的未知。
2. **长稳未验证。** 只在 01:12–01:30 的 3 局里观察到寿命本身（247/253/248s），**主动续命在真机上连续工作多轮的效果还没跑过**（也还没做过 30 分钟以上的长跑）。
3. **250s 是否对其它游戏成立。** 三局全是原神 `yssy`。换游戏（例如终末地）是否同样是 250s，**未测**。同一局里 L2 重连与手动重申请机位都产生了新会话，且都从新 `wsOpen` 重新计时，这一点在 §2 的会话 B / D 上有实证；但 `applySeat()` 之后的首个 `wsOpen` 与普通重连的 `wsOpen` 在服务端眼里是否等价，**未知**。
4. **`sess=` 的起点是 `wsOpen` 而不是「真正出画」。** 若某局 wsOpen 后很久才出画（弱网、IDR 等很久），230s 的续命可能落在「其实还没真正用满 250s 推流」的时刻 —— 这种情况下续命是**提前**的，代价只是多换一次会话，不会造成故障，但也没必要。
5. **服务端计时器的真实起点仍未定论。** 从 `wsOpen` 起算的 ±3s 是我们能观测到的最好拟合，但**没有网关侧证据**证明计时器就是绑在 WS 会话上（也可能是绑在 DTLS 会话、或某个我们看不到的服务端对象上，只是恰好同生命周期）。
6. **停推与「服务端 kickout」的因果关系仍未证实。** `BUG1-KEEPALIVE-PROTOCOL.md` 已判定「发 20015/20021」这条路走不通（`gameToken` 拿不到、通道接不上），本文档只是**绕过**它，不是修复它。
7. ~~**`renewNow()` 直接复用 `onReconnect()`**，所以它继承 `onReconnect` 的全部假设（复用 `gatewayUrl`、不重新申请机位）。~~ → **已更正（2026-11-14）**：`renewNow()` 现在走 `onReapply()`（重新申请机位），不是 `onReconnect()`。起因是 01:51:37 真机实测：复用同一 `gatewayUrl` 重连后，网关 5 秒即 `op=close data={"code":0,"reason":"normal"}` 把新会话关掉（同机位短时间内二次连被判重复连接）。改成换机位解决了「被踢」，但带来了「游戏重开」—— 这正是方案被默认关闭的直接原因（§9）。

8. **「换会话必然重开对局容器」这个性质，只在原神 `yssy` 上验证过三次。** 纯串流 / 没有对局容器的游戏是否也这样，**完全未测** —— 这是这套方案唯一可能翻案的余地（§9.6）。

## 9. 2026-11-14 02:09 真机结论：默认关闭

> 本节是**本文档的最终结论**。§1–§2 的判据（每 WS 会话约 250s）成立且仍然有用；§3–§7 的方案**已关闭**，只作存档。

### 9.1 怎么测的

把 `ACTIVE_RENEW_MS` 从 `230000` 临时降到 `60000`（只为在几分钟内连做三轮，不是要改成 60s），原神 `yssy`，2026-11-14 02:09–02:13 连续三次。三次都**准点触发**，说明机制本身工作正常：

| # | 触发时刻 | 当时 `sess=` | 走的路径 |
|---|---|---|---|
| 1 | 02:10:37 | 60s | `onReapply()` 重新申请机位 |
| 2 | 02:11:49 | 60s | `onReapply()` 重新申请机位 |
| 3 | 02:13:01 | 60s | `onReapply()` 重新申请机位 |

### 9.2 代价：游戏从头开始（致命）

每次换机位都**重新拉起一个对局容器**，日志里 `[play] 出画 1280x720 audio=0` 会重新打一次 —— 注意 `audio=0`，新容器连音频轨都要重新协商。玩家看到的不是「黑一下接着玩」，而是**回到游戏启动画面、进度清零**。

三次实测的用户可见代价：

| # | 黑屏时长 | 音频恢复耗时 | 游戏进度 |
|---|---|---|---|
| 1 | 9s | 11s | **全部丢失** |
| 2 | 8s | 19s | **全部丢失** |
| 3 | 7s | 18s | **全部丢失** |

把这两组数字放在一起看：

| | 触发时机 | 用户代价 |
|---|---|---|
| 主动续命 | 每 230s（**必然发生**） | 游戏重开、进度清零、黑屏 7~9s、音频 11~19s |
| 不续命（交给 STALLGUARD） | 每 ~250s 停推后 | 静止画面约 8s + L2 黑屏，**实测停推→恢复 ≈ 11s，进度不丢** |

为了规避一个 250s 后才发生的停推，每 230s 主动打断一次对局 —— **不可接受**。而且不续命那一路的恢复时间已经被收紧后的 STALLGUARD 压到同一量级（约 11s），主动续命连「更快」这个优点都没有了。

### 9.3 另一条路也不通：`onReconnect()` 复用旧网关会被踢

最初的 `renewNow()` 用的是 `onReconnect()`（复用同一个 `gatewayUrl`，不换机位），本来指望它「无缝」。2026-11-14 01:51:37 真机实测：

```
op=close data={"code":0,"reason":"normal"}     ← 续命后 5 秒，网关主动关掉新会话
```

网关把「同一机位短时间内第二次连」判成重复连接直接关掉。于是那次的用户体感是「230s 黑 3s → 被踢 → 再等约 40s 靠 L3 救回」，**比不续命（250s 停推后约 25s 恢复）更差**。

改成 `onReapply()` 之后确实不再被踢，但换机位就换来 9.2 的「游戏重开」。**两条续命路径因此都走不通**：

| 路径 | 结果 |
|---|---|
| `onReconnect()`（复用网关） | 同机位二次连被网关 `op=close` 踢掉 |
| `onReapply()`（换机位） | 不被踢，但对局容器重拉，游戏从头开始 |

### 9.4 决策

```
ACTIVE_RENEW_MS = 0     ← 默认关闭（PenCG/src/pages/play/play.vue:265）
```

- **实现全部保留**：`checkRenew()` 的十二条门、`renewNow()` 的动作序列、probe 行的 `sess=` / `renew=` 字段、`wsOpenAt` / `renewAt` / `renewCount` 三个状态，一行没删。
  - 保留的理由：`sess=` 本身是**判断「是不是会话寿命到期」的唯一计时器**，即使不做主动续命也要它；而门与动作序列是将来万一找到「换会话不重开容器」的办法时能直接接上的东西。
- **重新启用只需改回 `230000`**，`checkRenew()` 门 2 立刻放行。
- **停推改由 STALLGUARD 兜底**：`STALL_RX_MS` 20000 → **8000**、`STALL_L1_WAIT_MS` 5000 → **3000**。单次代价从「游戏重开、进度清零」降到「黑屏约十几秒、**进度不丢**」。2026-11-14 02:19 起真机实测：停推 → 完全恢复约 **11 秒**（原来 25 秒以上）。详见 `docs/BUGFIX-bug1-stallguard.md`。

### 9.5 一句话

**阈值推导没错，错的是「换会话的代价」被低估了。** 当时按「重连 + 等新 IDR ≈ 2~4 秒」估算，实测是「重拉对局容器 = 游戏从头开始」。所以这个方案不是「还没调好」，而是**在这条产品线上不该存在**。

### 9.6 唯一可能翻案的余地（未测）

9.2 的结论全部来自原神 `yssy` 的三个样本。如果存在**没有对局容器、纯串流**的游戏（换机位不需要重启游戏状态），主动续命就可能重新变得划算。这个假设**完全没验证过**，也没有可用的游戏清单。

重新启用前必须先回答：换会话之后，游戏是否从启动画面重来？如果答案是「是」，就别启用。

### 9.7 与 §6.2 的关系

§6.2 的「关闭」写于本方案还默认启用的时候（那时是教读者怎么临时关掉）。现在是**反过来**：默认关闭，§6.2 讲的是怎么临时打开。两节内容已同步，但 §6.2 保留原有措辞结构，以本节为准。
