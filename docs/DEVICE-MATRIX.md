# 多机型真机测试清单

市场新规第 4 条要求「多机型适配：真机测试布局与字号」。本文给出机型档案、测试项矩阵、布局与字号专项、执行步骤与记录模板。

**先说清一个关键事实（2026-11-14 更新，已含 X6 Pro 真机实测）**：PenCG 此前**没有任何机型探测代码**，画布宽度写死 960。现已新建 `PenCG/src/services/device_profile.js` 并在 `src/app.js` 的 `onLaunch` 里同步取值，探测通道是 `$falcon.env`（字段清单见 `PenCG/native/iot-miniapp-sdk/include/JQuickEnv.h:14-26`），**探测失败一律退回 960**。

真机实测结论（详见 §1.2.1）：`$falcon.env` **读得到**，但它报的 800×480 / `deviceModel="HaaS UI"` 是**框架默认值，不是硬件真值**，因此被可信度闸门丢弃，落回 960。**也就是说：这条自动探测通道在本固件上不通，X7 Pro 只能靠 `FORCE_WIDTH` 手工指定宽度。** X6 Pro 上实测零回归（逐像素比对 diff>30 像素数 0、最大差 0）。

但这**不等于「支持多机型」**：
- `$falcon.env` 在 JS 层能否读到值，**尚未真机验证**；
- X7 Pro **一次都没测过**；
- 布局侧仍硬编码（`src/styles/base.less` 的 `.page` 960px、`.bar` 76px、`.content` 884px；`src/services/media.js:273`/`:495` 的 960×266），即使探测出 936 也会溢出 24px。

所以本文的测试清单仍是**必要的保障手段**，只是从「唯一」变成了「与运行时探测互补」。详见 §1.2.1 与 §7。

#### 1.2.1 PenCG 侧的适配代码现状（2026-11-14）

已新建 `PenCG/src/services/device_profile.js`，把「画布宽度 960」从硬编码改成「启动期探测 + 兜底」：

| 项 | 现状 | 证据 |
| :-- | :-- | :-- |
| 探测通道 | `$falcon.env` 的 `deviceWidth` / `deviceHeight` / `deviceModel` / `platform` / `apiVersion`。**实测：可读，但只报框架默认值 800×480，无硬件真值** | 字段名来自 `PenCG/native/iot-miniapp-sdk/include/JQuickEnv.h:14-26`（含样例 JSON）；**X6 Pro 真机 2026-11-14 00:23 实测 `raw=800x480 envModel=HaaS UI platform=Linux api=1`** —— 800×480 是 HaaS 通用参考分辨率，与本机视口 960×266、面板 480×960 都不符 |
| 可信度闸门 | 只有 `width ≥ 600 && height > 0 && width / height ≥ 2.2` 才采信 | 两台的物理面板都是 480×960（宽高比 ≤ 2），一旦 env 报的是面板而非视口，必须整组丢弃；只丢宽会把 480×960 的 960 当成高度用。**实测已起作用**：800×480 宽够 600 但宽高比 1.67 < 2.2，被正确拦下 → `source=fallback` |
| 兜底 | 任何异常 / 不可信 → 回到 **960** | 与改动前行为完全等价 |
| 覆盖通道 | 优先级 `FORCE_WIDTH` > `$falcon.env.custom.pencgDesignWidth` > `$falcon.env` > 兜底 960 | 前者要重新打包；后者（`custom`）只需在真机上 `$falcon.env.custom.$set('pencgDesignWidth', 936)` 并重启小程序，就能**在 X6 Pro 上伪造 X7 Pro 的 936 宽度**去观察布局溢出，是伪机型验证最省事的一条路 |
| 布局弹性 | **未做，且已成为唯一阻塞项** | `src/styles/base.less` 仍硬编码 `.page` 960px / `.bar` 76px / `.content` 884px；`src/services/media.js:273`、`:495` 仍硬编码 960×266；`src/pages/play/play.vue` 三栏 243+473+244=960。**在自动探测通道被证伪后，这里就是 X7 Pro 适配的全部工作量** |

> **真机结论（2026-11-14 00:23，X6 Pro，1.2.0 包含 `device_profile.js`）**
>
> 日志原文：
>
> ```
> [pencg][I] [device] width=960 height=266 source=fallback model=- raw=800x480
>   envModel=HaaS UI platform=Linux api=1
>   note=env 800x480 model="HaaS UI" platform="Linux" api=1 → 退回 960
> ```
>
> 由这条日志确定的三件事：
>
> 1. **`$falcon.env` 确实可读** —— 不是 `raw=null`，最坏的「通道完全不通」没有发生。
> 2. **但报的是 800×480 / `deviceModel="HaaS UI"` / `platform=Linux`**：既不是视口 960×266，也不是物理面板 480×960。800×480 是 HaaS 的通用参考分辨率，**这是框架写死的默认值，与真实硬件无关**。
> 3. **闸门正确拦下了它**，落回 960，X6 Pro 上视觉零回归（逐像素比对：diff>30 的像素数 **0**、最大差 **0**，与改动前完全一致）。闸门逻辑不需要改。
>
> **因此：这条通道对「视口自适应」没有实用价值 —— 读得到，但不含真值。** 保留它的理由只有两个，都与自适应无关：(a) 万一某个固件的 env 真填了真值，现有代码无需改动就能自动生效；(b) 它给出的一行日志比 `raw=null` 更有信息量，能区分「通道不通」和「通道通了但只会喊 800×480」这两种完全不同的现场。

> **仍然未验证的二条**：
> 1. **X7 Pro 一次都没跑过**，它的 env 报什么完全未知（连是否也报 800×480 都未测）。
> 2. **机型名可能根本不含型号数字**：X6 Pro 真机 `/proc/device-tree/model` 读到的是 `Rockchip RK3562 MELON LP4 V10 Board`（OEM 板名，无 `X6`/`X7` 字样），`/etc/miniapp/resources/local_deviceinfo.json` 的 `device_name` 是空串。所以 `KNOWN_MODELS` 的机型识别**很可能永远匹配不上**，日志里 `model=-` 属于正常现象，**不要**当作探测失败的判据 —— 判据只看 `source=` 与 `raw=`。

> **已排除的疑虑**：曾担心 `setViewPort` 与探测同在 `onLaunch` 会因 `JQuickFalconEnv::init()` 晚于 `App.onLaunch` 而静默落兜底（表现为 `raw=null`）。真机日志里 `raw=800x480` 证明**时序不是问题**，`onLaunch` 时 env 已就绪。

> 代码保证了「探测失败 = 行为与改动前完全一致」，但**不等于 X7 Pro 能正常显示** —— 见 §7。

## 3. 布局与字号专项

### 3.1 为什么这两项必须单独测

字号已全量改为 `vw`（175 处）。`vw` 的含义是「按视口宽度的百分比」，所以：

- X6 Pro：`1vw = 9.6px`
- X7 Pro：`1vw = 9.36px`（936 × 1%）

**同一个 `1.1458vw`（原 11px）在 X7 Pro 上是 10.73px**，比 X6 Pro 小约 2.5%。这是 vw 的设计意图（随视口缩放），不是 bug。但反过来：

> **在 X6 Pro 上刚好贴边的文案，到 X7 Pro 上会变宽松；在 X6 Pro 上就已经溢出的文案，到 X7 Pro 上可能刚好合格 —— 也就是说，「X6 Pro 上没有溢出」不能推出「X7 Pro 上也没有」，反之亦然。必须分别测。**

**取证方式（可复现）**：在 `PenCG/src/pages/diag/diag.vue` 临时加 3 行字形对照（`A…·—B` / `E● F⌫` / `G→H ★I`），构建装机后用 `miniapp_cli capture` 截图，放大 6 倍逐字辨认。证据：`.tmp/g1.png` + 放大图 `.tmp/g1_zoom.png`。**该 3 行已删除**（`diag.vue` 现 720 行，`grep -c gchk` = 0），下次复测照此重加即可。

**对应到具体位置的两项结果**：

| 位置 | 字符 | X6 实测 | 处置 |
| :-- | :-- | :-- | :-- |
| `PenCG/src/pages/play/play.vue:80` 自绘键盘删除键 | 原 `⌫` U+232B | **tofu** | 已改为中文「删」，键宽与字号未变 |
| `PenCG/src/pages/login/login.vue:107` 密码掩码 | `●` U+25CF | **正常** | 保留，不改 |

**结论**：

- 「不是 emoji 码段 ⇒ 一定有字形」这个推断是**错的**。`⌫` 是单色几何符号、无变体选择符、不属于任何 emoji 码段，却是唯一渲染成 tofu 的那个。
- 杂项技术符号区段 **U+2300–U+23FF**（`⌫` `⇧` `⌘` `⏎` `⇥` 等都在这段）在 X6 Pro 上**整体不可信**，进 UI 前必须逐个实测。
- 需要这类语义时用中文词（删 / 回车 / Tab）或 PNG 图标，不要指望字符本身。
- 上面标 ✅ 的 6 个字符可以放心用在 UI 文案里。

判据：UI 上显示为**可辨认的字形或图形**，不出现空白方框（tofu）、彩色 emoji 字或宽度异常的间隙。

> **X7 Pro 那一列全部待测。** PenCG 从未在 X7 Pro 上跑过（见 §7），不要把 X6 的结论直接外推到 X7 —— 两台机器是不同固件、不同系统字体。

#### 4.1.1 机型探测自检（每次装机后必做第一步）

`src/app.js` 的 `onLaunch` 现在会无条件打一行设备档案日志。装机启动后先看这一行，它记录本机 env 到底给了什么：

```
$ADB shell "grep -h '\[device\]' \"$L\" | tail -n 5"
```

**X6 Pro 实测（2026-11-14 00:23，1.2.0）就是这个形态**，对应下表第 3 行：

```
[pencg][I] [device] width=960 height=266 source=fallback model=- raw=800x480
  envModel=HaaS UI platform=Linux api=1
  note=env 800x480 model="HaaS UI" platform="Linux" api=1 → 退回 960
```

| 日志形态 | 含义 | 后续动作 |
| :-- | :-- | :-- |
| `[device] width=<非960> ... source=env` | env 可读且通过闸门，报出的值被当作视口 | 记录 `raw=`，并按 §3.2 逐项核对布局是否溢出（`base.less` 仍按 960 写死） |
| `[device] width=960 ... source=fallback ... raw=null` | env 读不到，或通道整个不通 | 画布仍是 960，功能不受影响；本机型只能靠 `FORCE_WIDTH` 人工适配 |
| `[device] width=960 ... source=fallback ... raw=800x480` | **X6 Pro 实测值**：env 可读，但报的是框架默认值 800×480（`deviceModel="HaaS UI"`、`platform=Linux`），宽高比 1.67 被闸门丢弃 | **这是当前固件的正常表现**，不是故障；自适应这条路在本固件不通（见 §7）。X6 视觉与改动前逐像素一致（diff>30 像素数 0、最大差 0） |
| `[device] width=960 ... source=fallback ... raw=480x960` | env 报的是**物理面板**尺寸，被闸门丢弃 | **预期**行为（否则会 `setViewPort(480)` 导致整页放大 2 倍） |
| `[device] width=... source=custom` | 有人在真机上 `$falcon.env.custom.$set('pencgDesignWidth', N)` 做了免构建覆盖 | 这是伪机型验证手段，见 §1.2.1 覆盖通道；验完务必 `$set('pencgDesignWidth', 0)` 清掉（会持久化） |
| 完全**没有** `[device]` 行 | `onLaunch` 里日志块异常，或日志文件不是这个 | 先确认落盘文件路径（见 `docs/DEV.md`），再查 `[pencg][life] app onLaunch viewport=` 那行在不在 |

**记录要点**：`model=-` 是**正常**的（机型名不含型号数字，见 §1.2.1「仍然未验证」第 2 条），不要当作失败判据。真正要记的是 `raw=` 和 `source=` 两个字段。

### 4.2 安装包

```

./env/adb/adb.exe shell "miniapp_cli install /tmp/8002026110200003.1_1_1.amr"

### 4.3 逐项测试

按 §2 的矩阵顺序执行。每项记录「通过 / 失败 / 未测」，失败的立刻拉日志。

**关于截图，先说清一个限制**：设备上**没有任何办法截到 KMS 视频平面**。已试过的四条路全部失败：

| 方法 | 结果 |
| :-- | :-- |
| `miniapp_cli capture` | 只抓 UI 图层，视频区是空的（另外背光关闭时会返回 `ret:0` 但只有 1086 字节纯白，截前要先 `hal-screen on`） |
| `miniapp_cli captureFB` | 返回 `{"ret": -1}`，**不可用** |
| `kmsgrab` | `rc=124`（超时/挂死） |
| `/dev/fb*` | 设备上没有该节点 |

所以：**UI 用 `capture` 截图；视频画面是否正常只能用「DRM `fb` 编号是否交替」间接判断（见 §4.4），或者靠人眼**。不要为了「留证据」去反复试 `captureFB`。

```
# UI 截图（视频区会是空白，这是预期的）
./env/adb/adb.exe shell "hal-screen on"
./env/adb/adb.exe shell "miniapp_cli capture /tmp/shot.png"
./env/adb/adb.exe pull /tmp/shot.png ./shots/x6pro-$(date +%H%M%S).png

# JS 日志（只有 console.error 落盘）
$ADB shell "grep -a -n 'pencg' \"$L\" | tail -50"

# native 日志（[cgmedia] 与 [pencg] 同一个文件，就是 $L；不要另找第二个文件）
$ADB shell "grep -a -n '\[cgmedia\]' \"$L\" | tail -50"
```

### 4.4 播放页专项取证

画了不动 / 黑屏时，最快的判据是看 DRM 的 `fb` 编号是否交替：

```
# 每 1 秒采一次，看 fb 是否变化
for i in $(seq 1 20); do
  ./env/adb/adb.exe shell "grep -A6 'Esmart1-win0' /sys/kernel/debug/dri/0/state | grep -o 'fb=[0-9]*'"
  sleep 1
done
```

- `fb` **持续交替**（如 127/130 交替）= 画面在翻页，正常。
- `fb` **恒定不变** = 平面绑着但不更新（历史 bug：`kmssink sync=true`，现已修为 `sync=false`，见 `cm_gst.c` 的 `KMS_SINK_PROPS` 宏）。

## 6. 已知机型风险（供测试时重点盯）
