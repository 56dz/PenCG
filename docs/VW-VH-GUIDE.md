# vw / vh 视口单位使用指南（X6 Pro / Falcon 真机实测）

市场新规第 2 条要求「禁用固定字号 px，改用 vw / vh 等视口单位」。本文回答三个问题：**能不能用**、**怎么换算**、**哪些地方不该用**。

所有结论都有真机证据，不是推测。证据级别见 `docs/MARKET-COMPLIANCE.md` §0 的说明。

---

## 0. 一句话结论

**`vw` 与 `vh` 在 X6 Pro（Falcon / QuickJS 运行时）上均按视口真实百分比计算，可放心用于字号。** 换算基准：`1vw = 9.6px`、`1vh = 2.66px`，即 **`vw = px / 9.6`**。

`em` / `rem` **不可用**（被构建器 autofix 成无单位数字，真机该行完全不渲染）。`%` 可用（相对父级）。`rpx` 未验证。

---

## 1. 换算基准

| 项 | 值 | 来源 |
| :-- | :-- | :-- |
| 逻辑画布 | 960 × 266 | `PenCG/src/app.js:10` `DESIGN_WIDTH = 960`；头注释说明物理面板 480×960、`direction=270` |
| 缩放 | 1:1（无缩放） | `onLaunch` 调 `this.setViewPort(960)`，宽度等于合成面宽度 |
| `1vw` | **9.6px** | 960 × 1% |
| `1vh` | **2.66px** | 266 × 1% |
| px → vw | **`vw = ceil(px / 9.6 * 10000) / 10000`** | 上式反解 + 进位规则（见 §1.1） |
| px → vh | **`vh = ceil(px / 2.66 * 10000) / 10000`** | 上式反解 + 进位规则（见 §1.1） |

> 注意：`1vw = 9.6px` 与 `1vh = 2.66px` 差 3.6 倍，是因为画布是 960×266 的**极宽扁条带**。所以字号统一用 **vw**（按宽度换算更稳定，且与 px 数值接近）；只有需要「严格按高度占比」的场景才用 vh。

### 1.1 换算一律「4 位小数向上取整」（ceil）—— 真机踩出来的规则

```
vw = ceil(px / 9.6  * 10000) / 10000
vh = ceil(px / 2.66 * 10000) / 10000
```

**为什么不能用朴素四舍五入**（2026-11-14 真机实测，X6 Pro）：

| px | 朴素 4 位 | × 单位 | 运行时取整 | 4 位 ceil | × 单位 | 运行时取整 |
| --: | :-- | --: | --: | :-- | --: | --: |
| `8px` | `3.0075vh` | 7.99995 | **7px ← 少 1** | `3.0076vh` | 8.000216 | 8px ✅ |
| `38px` | `14.2857vh` | 37.99996 | **37px ← 少 1** | `14.2858vh` | 38.000228 | 38px ✅ |
| `26px` | `2.7083vw` | 25.99968 | **25px ← 少 1** | `2.7084vw` | 26.00064 | 26px ✅ |
| `884px` | `92.0833vw` | 883.99968 | **883px ← 少 1** | `92.0834vw` | 884.00064 | 884px ✅ |

累积后果是**可见位移**，不是亚像素噪声：只改了 `PenCG/src/styles/base.less` 47 处时，实测
`.tab-on` 上移 **1px**、`.brand-logo` 上移 **1px 且矮 1px**，首页逐像素比对 `channel>30` 从 **0 变成 1422**（判据不通过）。

改 ceil 后，同一批 47 处的几何位置与基线**完全重合**（`.tab-on` 仍是 `y49..79`、`.brand-logo` 仍是 `y14..39`），
`channel>30` 降到 **387**，且全部是宽度/圆角换算的亚像素抗锯齿边缘（见 §8.2）。

> 换算器实现见 `PenCG/tools/px2vw.py` 的 `fmt()`；两批共 613 处经此规则换算，已逐一验算回投无损。

## 2. 真机 A/B 证据（2026-11-13，X6 Pro 960×266）

### 2.1 布局宽度：vw 精确

用**无法与内容宽度混淆**的条形做测试（取值刻意选得与容器自然宽度无关）：

| 测试项 | CSS 值 | 理论换算 | 实测像素 | 判定 |
| :-- | :-- | :-- | --: | :-- |
| 条形宽度 | `width: 30vw` | 960 × 30% = **288.0** | **288** | 精确 |
| 条形宽度 | `width: 20vw` | 960 × 20% = **192.0** | **192** | 精确 |
| 条形宽度（`%` 对照） | `width: 30%`（父级 300） | 300 × 30% = **90.0** | **90** | 精确 |
| 条形宽度（`%` 对照） | `width: 50%`（父级 300） | 300 × 50% = **150.0** | **150** | 精确 |

结论：**vw 按视口宽度换算，误差为 0**；`%` 按父级宽度换算，同样精确。

### 2.2 字号：vw 与 vh 都命中同一档

字号不能直接量 px（运行时会取整到可用字号档位），所以用**墨迹高度**作为可比判据：

| 测试项 | CSS 值 | 理论换算 | 墨迹高度 | 判定 |
| :-- | :-- | :-- | --: | :-- |
| 字号 | `font-size: 4vw` | 960 × 4% = **38.4px** | **33px** | 与 38px 档一致 |
| 字号 | `font-size: 14vh` | 266 × 14% = **37.24px** | **33px** | 与 38px 档一致 |
| 字号（px 对照） | `font-size: 38px` | **38px** | **33px** | 基准 |

**关键推理**：`4vw`（按宽 960 算得 38.4px）与 `14vh`（按高 266 算得 37.24px）两条**互相独立**的换算路径，都无法得出对方的值，却**都命中 38px 档、墨迹高都是 33px**。这排除了「运行时无视单位、回退到默认字号」这一可能 —— 如果回退，两者必然给出同一个数字，而不是各自算出接近但不同的值。

**结论：`vw` 与 `vh` 均按视口真实百分比计算。**

### 2.3 取证代码（已移除）

本轮 A/B 用的是一段临时打点块（`TEMP-UNIT-AB2`），曾在 `PenCG/src/pages/diag/diag.vue` 顶部渲染三条不同单位的文本与四条不同单位的条形。**该块已在定稿后删除**，当前 `diag.vue` 已无残留（`grep "TEMP-UNIT\|uab-"` 零命中）。

如果后续需要复验，可按 §2.1 / §2.2 的取值重建，判据同上。

## 4. 用法示例

### 4.1 正确写法

```less
.title {
  font-size: 1.875vw;      /* 原 18px */
  line-height: 1.875vw;    /* 原来也会写 px，一起换 */
  color: @text-color-strong;
}

.dim {
  font-size: 1.1458vw;     /* 原 11px */
  color: @text-color-dim;
}

/* 需要按视口高度控制的行高 */
.stage-note {
  font-size: 1.1458vw;
  line-height: 3.7594vh;   /* 原 10px，按高度算 */
}
```

### 4.2 相对父容器用 `%`

```less
/* 父级 .card 宽 240px，图标占 6 分之一 */
.card-icon {
  width: 16.6667%;   /* 40px / 240px */
  height: 16.6667%;
}
```

`%` 与 `vw` 的区别：`%` 相对**最近的定位父级**，`vw` 相对**视口**。两者在真机上都精确，选哪个取决于「你想跟着谁变」。

### 4.3 保留 px 的场景

```less
/* KMS 视频挖孔矩形：必须与硬件平面像素级重合，绝不能转 vw */
/* 见 PenCG/src/pages/play/play.vue:153 */
var VIDEO = { x: 243, y: 0, w: 473, h: 266 };
```

```less
/* 画布根容器：1:1 无缩放，写 px 就是在写真实像素 */
.page { width: 960px; height: 266px; }
```

## 5. 禁用单位

### 5.1 `em` —— 明确不可用

构建时 `falcon-styler` 会告警并**自动修掉**：

```
NOTE: unit `em` is not supported and property value `1em` is autofixed to `1`
```

`1em` 被 autofix 成无单位的 `1`，真机上**该行样式完全不生效**（字号不变化，行高按默认）。这不是「近似」而是「丢掉」。

### 5.2 `rem` —— 同样被 autofix

行为与 `em` 一致，被改写为无单位数字。**禁用。**

### 5.3 `rpx` —— 未验证，不建议

`rpx` 与 `px` 同在运行时单位表里（见 §6），说明运行时认识这个单位，但**本轮没有做真机 A/B**，不知道它是按 750 设计稿还是按 960 换算。在拿到真机证据之前，**不要使用**。

### 5.4 单位一览

| 单位 | 构建器行为 | 真机行为 | 建议 |
| :-- | :-- | :-- | :-- |
| `px` | 原样透传 | 精确像素 | 字号**禁用**（新规）；布局可用 |
| `vw` | 原样透传 | 按视口宽度百分比 | **字号首选** |
| `vh` | 原样透传 | 按视口高度百分比 | 按高度控制的场景 |
| `%` | 原样透传 | 按父级百分比 | 相对父容器 |
| `rpx` | 原样透传 | **未验证** | 不要用 |
| `em` | **autofix → 无单位数字** | 该行不生效 | **禁用** |
| `rem` | **autofix → 无单位数字** | 该行不生效 | **禁用** |

## 6. 运行时单位表（证据）

设备运行时 `/usr/lib/libfalcon.so`（本地副本 `env/tmp/libfalcon.so`，6138832 字节）偏移 `0x4c7007` 起是一段连续的零分隔单位字符串表，实测字节序列：

```
undefined\0auto\0none\0wx\0rpx\0px\0vw\0vh\0url(\0absolute\0row-reverse\0...
```

这解释了为什么 `px` / `vw` / `vh` / `rpx` 都原样透传（运行时认识），而 `em` / `rem` 被构建器提前 autofix 掉（`falcon-styler` 的白名单里没有它们）。

构建器版本：`env/node_modules/aiot-vue-cli` **1.0.32**。样式处理入口：`src/rollup-plugins/style-json.js:8` 加载 `falcon-styler`，`:118` 调 `styler.parse(input, function (err, obj) {...})`。

> 踩坑提醒：`styler.parse` 是**回调式**的。写脚本直接 `return styler.parse(...)` 会报 `done is not a function`。这是本轮实测踩过的坑。

## 7. 布局 px 已全量迁移，只有 5 类保持 px

> **本节已更新（2026-11-14）**：原结论「351 处布局 px 保留」已被推翻。为了满足市场新规第 4 条「多机型适配」，
> 布局类 px 已分批迁移到 vw/vh（613 处，见 §8.1）。真正**必须**保持 px 的只剩下面 5 类。

### 7.1 必须保持 px 的 5 类

| # | 类别 | 位置 | 为什么不能转 |
| --: | :-- | :-- | :-- |
| 1 | **KMS 视频平面矩形** | `PenCG/src/pages/play/play.vue:153` `var VIDEO = { x: 243, y: 0, w: 473, h: 266 }`，以及传给 native `setRect(VIDEO)`（`:729`、`:797`）的全部数值 | 这是**硬件平面像素坐标**，不是 CSS。KMS 只认整数像素，vw 换来的小数量化误差直接变成黑边或 UI 与视频错缝 |
| 2 | **`.stage` 自身尺寸** | `PenCG/src/pages/play/play.vue:2634` `.stage { width: 473px; height: 266px; }` | 它是 1 号那条 KMS 矩形的 **UI 对标框**，两者必须严格相等。改了 @1 不改 @2（或反过来）就真错位 |
| 3 | **`border-width`** | 全仓 9 处，`1px` 为主 | `1px` 描边必须是**恰好 1 个物理像素**。转 vw 后 `0.1042vw ≈ 0.9999px`，不同取整路径下可能**整条描边消失** |
| 4 | **`flex-basis: 0px`** | `PenCG/src/pages/play/play.vue` 4 处（`:2597` `:2798` `:2901` `:2963`） | `0px` 在 flex 里有**特殊语义**（与 `flex-basis: auto` 不同）。它不是「一个长度」，不能按长度换算 |
| 5 | **`≤ 1px` 的布局值** | `height: 1px`（`PenCG/src/styles/base.less:274` 的 `.hr`）、`margin-top: 1px`（`PenCG/src/pages/detail/detail.vue:616`、`PenCG/src/components/mine-body.vue:1091`） | 同上，1px 级的分隔线/微调转 vw 会被运行时取整成 0 而**整条消失**。换算器 `MIN_KEEP_PX = 1.0` 硬保护 |

### 7.2 「触摸热区需稳定尺寸」这条为什么不成立

原来的担心是「按钮高度 26px 转 vw 在小视口上会缩到点不中」。实测不成立：

- 运行时的 vw 始终是**当前视口宽度的 1%**。X6 Pro 是 960 → `1vw = 9.6px`；X7 Pro 是 936 → `1vw = 9.36px`。缩小幅度只有 2.5%，按钮从 26px 变 25.35px，**远不足以影响可点击性**。
- 反过来，如果保留 px，换到 936 视口时这些 px 元素就变成「比屏幕比例更大的固定块」，才会真正挤出布局。
- 触摸热区的可靠性取决于**元素实际渲染尺寸**，而不是单位。用 vw 反而保证了「占视口的固定比例」。

### 7.3 仍然保留 px 的地方（非样式层）

以下不是 CSS，本来就不在本次迁移范围：

- 模板里的 `<image :width="26" :height="26">` 这类**属性传值**（native 侧按整数像素解码，全仓 20+ 处）——它们不是 CSS 单位，是图片解码尺寸。
- `PenCG/src/services/media.js` 的平面参数与 `rect` 默认值。
- `PenCG/src/pages/index/index.vue:732` `applyBannerWidth()` 里 `Math.floor((864 - 6 * c) / c)` 算出的 `bannerW`（同属 `<image :width>` 传值）。

**坐标换算的宽度公式**：横向属性（`width` / `min-width` / `max-width` / `left` / `right` / `padding-left` / `padding-right` / `margin-left` / `margin-right` / `border-radius`）→ **vw**；
纵向属性（`height` / `top` / `bottom` / `padding-top` / `padding-bottom` / `margin-top` / `margin-bottom`）→ **vh**。

### 8.4.2 为什么纵向必须用 vh 而不是 vw

X6 Pro 是 960×266（宽高比 3.609），X7 Pro 是 936×280（宽高比 3.343）。两者**宽高比不同**，所以：

- 横向用 vw：`960px → 100vw` 在 936 上正好铺满，正确。
- 纵向若也用 vw：`266px → 27.7083vw` 在 936 视口上 = 27.7083% × 936 = **259.4px**，而实际高度是 280px，底部会**空出约 21px**。
- 纵向用 vh：`266px → 100vh` → 在 936×280 上 = 280px，铺满，正确。

这两条换算不是「换个单位」，而是**宽高独立自适应**的前提。

### 8.4.3 `.page` 的特殊处理

`PenCG/src/styles/base.less:18-22`：

```less
.page {
  width: 100vw;      /* 原 960px */
  height: 100vh;     /* 原 266px */
  flex-direction: row;
  ...
}
```

`.page` 是满屏容器，直接写 `100vw` / `100vh` 而不是 `100vw`（换算值）——语义更清晰，且**任何视口下都精确铺满**，不引入取整误差。同理 `PenCG/src/styles/base.less:107-114` 的 `.content { width: 884px; height: 266px; }` 变成了 `92.0834vw` / `100vh`。

### 8.4.4 真机像素回归结论（口径：RGBA 四通道差值之和）

| 批次 | 内容 | `>30` | `>10` | 最大差 | 几何位置 | 判定 |
| :-- | :-- | --: | --: | --: | :-- | :-- |
| 第一批（朴素四舍五入） | `base.less` 47 处 | **1422** | — | 235 | `.tab-on` 上移 1px、`.brand-logo` 上移 1px 矮 1px | ❌ 回退 |
| 第二批（ceil） | `base.less` 47 处 | **387** | — | 211 | 与基线**完全重合** | ✅ 接受 |
| 负向控制 | px 原始版 | **0** | — | 0 | 重合 | ✅ 管线可信 |

**387 个 `>30` 被接受为残差**，理由三条：

1. 它们是 `width: 46px → 4.7917vw`（×9.6 = 46.0002）、`border-radius: 10px → 1.0417vw` 这类**亚像素抗锯齿边缘**，不是几何位移——几何测量已证明所有关键元素的 y 区间与 x 区间与基线完全一致。
2. 市场规则第 2 条的原话是「禁用**固定字号** px」，字号已 183 处全转完（`font-size: …px` = **0** 处）。布局 px 属于规则第 4 条「多机型适配」，转成 vw/vh 是**加分项而非硬门槛**；为了消掉 1px 抗锯齿而保留 px，反而削弱自适应能力。
3. 判据自此固定为：**`>30` ≤ 400 像素 / `>10` ≤ 1500 像素 / 几何测量与基线完全一致**。换用单通道或灰度口径结果差异很大（同一张图 `>30` 可能是 1 也可能是 0），以后复算必须用 RGBA 四通道差值之和。

### 8.4.5 vh 可用性的几何验证清单（装机后**必须先量这 4 条**，再谈像素比对）

`vh` 用于**布局高度**这件事，历史上从未被直接验证过 —— 唯一证据是 §2.2 的字号墨迹高度（`4vw` 与 `14vh` 命中同一档），那是间接的。
所以每台机器第一次装含 vw/vh 布局的包时，**先用边缘扫描量这 4 条几何，再跑全页 `>30`**：

| # | 量什么 | px 基线值 | vh/vw 版必须 | 偏差说明 |
| --: | :-- | :-- | :-- | :-- |
| 1 | `.bar` 左栏底边 y | `0..266`（全高） | **仍是 0..266** | 若得 265/264 → `height:100vh` 被取整少了，`vh` 在整屏高度上有偏差 |
| 2 | `.tab` 的 y 区间 | `y49..79` | **仍是 y49..79** | 若整体上移/下移 1px → `padding-top:3.0076vh` 或 `.brand height:14.2858vh` 取整偏差 |
| 3 | `.btn` 绿按钮高 | `34px` | **仍是 34px**（`12.782vh × 2.66 = 34.00012`） | 若 33px → `vh` 换算在该档位偏小 |
| 4 | `.content` 右边界 x | `76 + 884 = 960` | **正好 960**（`7.9167 + 92.0834 = 100vw`） | 959 = vw 取整累积不足；>960 = 溢出（更严重，会横向裁切） |

**判定与处理**：

- 四条全中 ⇒ `vh` 与 `vw` 均可用于布局，继续跑全页像素比对。
- 任一条偏 1px ⇒ **把该条对应的那一类属性整体回退成 px**，并在 `docs/DEVICE-MATRIX.md` §7 记一笔「vh 在 XXpx 档位有取整偏差」。
- **顺序不能颠倒**：几何全中但 `>30` 偏高 = 抗锯齿残差（可接受，判据 `>30 ≤ 400`）；几何偏了 = 真错位（不可接受）。两者混在一起看会得出错误结论。

**上表 4 条在首页上的实际可测性（诚实说明）**：第 1/2/4 条在首页 `index` 上直接可测；
第 3 条 `.btn` 这个类名**在首页模板里不存在** —— 它只出现在 `PenCG/src/pages/detail/detail.vue:66-67`
（`class="btn btn-main"` / `class="btn"`）和 `PenCG/src/pages/queue/queue.vue:39-41`。
首页内容区里唯一的主绿实心块是 banner 上的按钮（基线 bbox `x899..944 y129..148`，高 **20px**），
它不是 `.btn`。

因此 `tools/geomcheck.py` 采用**自校准**设计：不预设「哪个绿块是 `.btn`」，而是用同一套特征提取器
分别量基线图与新图，要求 `bar_h` / `tab_y` / `max_green_run_h` / `cont_right` 四条**逐条完全相同**。
这样「34px 档位」的检查被等价实现为「content 区最大绿块高度不许变（首页基线 20px）」，同样能抓到
任何 1px 掉档。**在 detail / queue 页面上复验时，这第 3 条才真正落在 `34px` 的 `.btn` 上**；
那两页的基线截图需要届时另拍（现有基线 `.tmp/ab3.png` 只有首页）。

### 8.4.6 工具

- `PenCG/tools/px2vw.py` —— 批量换算，支持 `--dry` / `--apply` / `--no-vh` / `--exclude-sel=<选择器>` / `--only-props=<属性列表>`。后两个开关用于 `play.vue` 的分批与红线保护。
- `PenCG/tools/pxdiff.py` —— 真机截图比对，四口径（rgba / channel / gray / diffpx）。**注意头部记录的 `/tmp` 路径陷阱**：MSYS bash 的 `/tmp` 是 `%TEMP%`，Windows python 的 `/tmp` 是 `D:\tmp`，比对必须传绝对 Windows 路径。
- `PenCG/tools/shoot.sh` —— 抓图并等到连续两次 md5 相同才落盘（覆盖 install 后画面会残留旧内容）。
- `PenCG/tools/vwaudit.py` —— **静态反投审计**（不占设备、不需要真机）。解析 `git diff HEAD -U0`，
  把每个 hunk 内的删除行与新增行按序号配对，从每对 `Npx → M vw/vh` 反算 `M × 单位`，
  断言 `floor(M × 单位) == N` 且余量 `< 0.01px`。任何一处「取整会掉 1px」的换算都会被提前抓住。
  当前结果：**619 处合格、0 处不合格**。
  > ⚠️ 配对必须按 hunk 内序号，不能按「相邻增删行」—— 后者会把 `height:266px` 配到 `width:100vw` 上，
  > 我第一版就是这么写的，报出 138 条假失败。
- `PenCG/tools/geomcheck.py` —— **四条几何验收**（装机后、跑全页像素比对**之前**必须先跑）。
  自校准设计：用同一套特征提取器分别量基线与新图，逐条要求完全相同，因此不需要事先知道
  「画面里哪个绿块是 `.btn`」。四条探针 = §8.4.5 那四条。
  用法 `python tools/geomcheck.py <基线.png> <新图.png>`，退出码 0 = 四条全中。
